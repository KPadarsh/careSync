# CareSync Authentication Architecture (Phase 3)

This document specifies the real, database-backed authentication system for CareSync. The implementation follows strict server-side authority, cryptographically hashed passwords and session tokens, HTTP-only secure cookie transport, and zero client-supplied role trust.

---

## 1. Authentication Flow

```text
Login Request (email, password)
      ↓
[POST /api/auth/login]
      ↓
Input Validation (email format, non-empty)
      ↓
Email Normalization (lowercase, trimmed)
      ↓
MongoDB Query: User.findOne({ email }).select("+passwordHash")
      ↓
Account Status Verification:
  - SUSPENDED -> 403 Forbidden
  - INACTIVE  -> 403 Forbidden
  - Not ACTIVE -> 403 Forbidden
      ↓
Password Verification (timing-safe scrypt / crypto compare)
  - Failure -> 401 Unauthorized (generic error message prevents enumeration)
      ↓
Update User.lastLoginAt = new Date()
      ↓
Generate Cryptographically Secure Random Session Token (256-bit entropy)
      ↓
Hash Session Token with SHA-256 (tokenHash)
      ↓
MongoDB Write: Session.create({ userId, tokenHash, expiresAt, lastUsedAt })
      ↓
Set Secure HTTP-Only Cookie ("caresync_session")
      ↓
Return SafeUser Object (NEVER exposes passwordHash or raw session token)
```

---

## 2. Server-Side Session Architecture

CareSync implements **server-managed sessions** in MongoDB to ensure the database remains the sole authoritative source of truth for user accounts and access status.

### 2.1 The `Session` Model (`src/models/Session.ts`)

| Field | Type | Description |
|---|---|---|
| `_id` | `ObjectId` | Primary key |
| `userId` | `ObjectId` | Reference to `User._id` |
| `tokenHash` | `string` | SHA-256 hash of the session token. **Indexed (unique)**. |
| `expiresAt` | `Date` | Timestamp when the session expires. **TTL Indexed**. |
| `lastUsedAt` | `Date` | Timestamp of most recent activity. |
| `createdAt` | `Date` | Timestamp of creation. |
| `updatedAt` | `Date` | Timestamp of update. |

### 2.2 Security of Session Tokens

1. **No Plaintext Tokens in Database**:  
   The raw session token generated by `crypto.randomBytes(32).toString('hex')` is **never** saved to MongoDB. Only its one-way SHA-256 hash (`tokenHash`) is persisted. Even in the event of a database compromise, session tokens cannot be reversed.
2. **HTTP-Only Cookie Transport**:  
   The raw token is delivered to the browser exclusively through an HTTP-only, SameSite=Lax, secure-in-production cookie named `caresync_session`. Client-side JavaScript (`localStorage`, `sessionStorage`, `document.cookie`) has **zero access** to the token, mitigating XSS token theft.
3. **Session Verification Lifecycle**:  
   On every protected request, `AuthService.getCurrentUser()`:
   - Reads the raw session token from the HTTP-only cookie.
   - Computes `tokenHash = sha256(rawToken)`.
   - Queries `Session.findOne({ tokenHash })`.
   - Independently verifies `session.expiresAt > Date.now()` (does not rely solely on MongoDB's asynchronous TTL cleanup thread).
   - Queries `User.findById(session.userId)`.
   - Verifies `user.status === "ACTIVE"`. If an administrator marks an account `INACTIVE` or `SUSPENDED`, all existing sessions for that account immediately stop functioning.
   - Updates `session.lastUsedAt = new Date()`.
   - Returns the sanitized `SafeUser`.
4. **Session Invalidation (Logout)**:  
   When `POST /api/auth/logout` is called:
   - The token hash is calculated.
   - The session document is deleted from MongoDB (`Session.deleteOne({ tokenHash })`).
   - The `caresync_session` cookie is cleared with `maxAge: 0` and `expires: 1970-01-01`.
   - Replaying the old token immediately yields `401 Unauthorized`.

## 3. User Identity & Profile Relationship

The authentication identity is decoupled from clinical and operational profiles:

```text
               ┌─────────────────────────────────────┐
               │              User                   │
               │  - _id                              │
               │  - name                             │
               │  - email (unique)                   │
               │  - passwordHash (hidden)            │
               │  - role (authoritative)             │
               │  - status (ACTIVE/INACTIVE/SUSPEND) │
               │  - profileType ("Doctor"|"Staff"|...)│
               │  - profileId (ObjectId)             │
               └──────────────────┬──────────────────┘
                                  │
         ┌────────────────────────┼────────────────────────┐
         ▼                        ▼                        ▼
┌──────────────────┐     ┌──────────────────┐     ┌──────────────────┐
│     Doctor       │     │      Staff       │     │     Patient      │
│  - doctorId      │     │  - employeeId    │     │  - patientId     │
│  - departmentId  │     │  - departmentId  │     │  - phone, address│
│  - licenseNumber │     │  - designation   │     │  (userId optional│
│  - userId        │     │  - userId        │     │   for walk-ins)  │
└──────────────────┘     └──────────────────┘     └──────────────────┘
```

- **Authoritative Role**: `User.role` is the single source of truth for authentication and authorization.
- **Authoritative Status**: `User.status` controls login and request validity.
- **SafeUser Model**:
  ```typescript
  interface SafeUser {
    id: string;
    name: string;
    email: string;
    role: string;
    status: string;
    profileType?: string;
    profileId?: string;
    avatar?: string;
    phone?: string;
    lastLoginAt?: Date;
  }
  ```

## 4. Security Rules & Guarantees

1. **Zero Client Trust**:
   - The client browser never supplies the user's role, permissions, status, or identity.
   - URL parameters like `?role=admin` or storage entries like `localStorage.role` are ignored.
   - Role-based routing is resolved on the server from the MongoDB `User.role`.
2. **Password Protection**:
   - Plaintext passwords are never stored, logged, or serialized.
   - Passwords are salted and hashed using scrypt with timing-safe comparison (`crypto.timingSafeEqual`).
   - The User schema has `passwordHash: { select: false }`, ensuring query results never accidentally expose the hash.
3. **No Account Enumeration**:
   - Incorrect passwords and non-existent emails return the identical error: `"Invalid email or password."` with HTTP status `401`.
4. **Inactive & Suspended Accounts**:
   - Accounts with status `INACTIVE` or `SUSPENDED` are rejected during login (HTTP 403).
   - If an account becomes inactive while a session is alive, the next request fails because `getCurrentUser()` verifies the database record on every request.
5. **No Demo Credentials**:
   - No hardcoded `admin@caresync.com`, default passwords, or fake users exist.

## 5. Endpoints Summary

| Method | Endpoint | Description | Auth Required |
|---|---|---|---|
| `POST` | `/api/auth/login` | Authenticate with email & password, create session | No |
| `POST` | `/api/auth/logout` | Invalidate session in MongoDB, clear cookie | Yes |
| `GET` | `/api/auth/me` | Return currently authenticated `SafeUser` | Yes |
